# Dottie

Dottie runs **dotties**: persistent personal agents (LangChain Deep Agents) that sleep almost all the time and wake on a message,
a schedule or another dottie's message. Each has a personality, skills, toolkits, a PostgreSQL-backed wiki as long-term memory and
an optional sandbox (docker locally, Azure Container Apps Sandboxes on Azure). See README.md for the architecture.

FastAPI backend (`src/dottie/`), React + Vite frontend (`frontend/`) served by the backend as one app, PostgreSQL with Alembic migrations.
Python with uv, ruff and pyright.

## Commands

```bash
scripts/check.sh [--fix]          # THE quality gate (= CI): ruff, pyright, pytest, API types, prettier, oxlint, tsc, bicep
scripts/versions.sh               # what is outdated: packages, runtimes, actions, Bicep API versions
scripts/run-local.sh [--dev]     # run the app on :8370; --dev adds Vite hot reload on :5173
scripts/db.sh up|down|reset|psql  # the local PostgreSQL container (port 54845)
scripts/db.sh revision "add x"    # a migration, autogenerated from models.py: read it before applying
scripts/db.sh migrate             # apply migrations (the app also does this at startup, under a lock)
cd frontend && npm run gen:api    # regenerate the API client (src/client/) after any API change
scripts/azure-up.sh [rg] [region] / scripts/azure-down.sh [rg]   # Azure Container Apps (ask first: costs money)
uv add PKG / uv add --dev PKG     # never pip; never edit uv.lock by hand
```

## Git workflow

- Work on a branch, never on `main`: `git switch -c <short-topic>` before the first change of a task.
- **Commit and push only when the user says so.** Don't commit "to save progress"; don't open or merge PRs unasked.
- Before proposing a commit, `scripts/check.sh` must pass.
- Commit messages: `Area: what changed` (imperative, under 72 chars), then a body explaining *why* and anything
  surprising. One logical change per commit. PRs are squash-merged with the same style.

## Layout

- `src/dottie/config.py`: every setting, from env/.env. A new setting also goes into `.env.example` (a test checks).
- `src/dottie/api/`: `app.py` builds the app (`create_app(settings, model_factory, provider)`); one router module per area
  (dotties, chat, wiki, schedules, skills, activity, system); `errors.py`.
- `src/dottie/engine/`: the part that is always awake. `bus.py` (messages = the only way to wake a dottie), `scheduler.py`,
  `core.py` (dispatcher + leader lock), `runner.py` (one waking), `agent.py` (model, prompt, Deep Agent), `tools.py` (toolkits),
  `files.py` (wiki + skills as the agent's filesystem), `sandboxes.py`, `mcp.py` (MCP servers a dottie uses), `seed.py`.
  `src/dottie/mcp_server.py` is Dottie as an MCP server (`/mcp/`).
- `src/dottie/models.py`: SQLAlchemy models. `db.py`: engine, session dependency, migrations. `migrations/`: Alembic.
- `tests/`: pytest, one file per area, against a real PostgreSQL (`scripts/db.sh up`).
- `frontend/src/`: `pages/` (one per screen), `components/`, `client/` (generated from the API: types, SDK and
  TanStack Query options; never edit), `lib/api.ts` (client setup, `ApiError`), `index.css` (design tokens, light and
  dark). Server data goes through TanStack Query with the generated `...Options()` / `...Mutation()`.
- `infra/main.bicep`: all Azure resources. `scripts/azure-*.sh` deploy and remove; state in `.azure/` (git-ignored).

## Conventions

- **Simple first.** The smallest change that solves the problem. No abstraction until the third repetition; no
  options nobody asked for; no speculative layers (repositories, services, factories) over FastAPI and SQLAlchemy.
- **One source of truth.** Settings live in `config.py`.
  API types come from the backend's Pydantic models via OpenAPI (`npm run gen:api`), never written twice.
  The schema lives in `models.py` and reaches the database only through migrations.
- Delete dead code instead of commenting it out; remove what a change makes unused.
- Errors: raise `ApiError(code, message, status)`; the client always gets `{"error": {"code", "message"}}`.
- Type everything (`Annotated[..., Depends()]` for dependencies, Pydantic models in and out of every route).
- Comments say *why*, not what. Docstrings on modules and on anything non-obvious.
- Tests: a test next to every behaviour change, through the HTTP API where possible. Fakes for external services,
  never mocks of our own code. Never a real model: `tests/fakes.py` scripts what each dottie says (`scripts` fixture), and
  `client.app.state.engine.tick()` + `wait_idle()` let the engine look for work (it does not run by itself in tests).
- Migrations: never edit one that has been applied anywhere but your machine; add a new one. Read every
  autogenerated migration (renames come out as drop + add). Downgrades must work (`tests/test_migrations.py`).
- Secrets live in `.env` (git-ignored) and in Container Apps secrets; never in code, logs or chat.

## Things that are easy to get wrong

- A dottie's answer is delivered to the user only for chat and schedule conversations. In a dottie-to-dottie thread the
  answer is dropped on purpose (it would loop): dotties use `send_message`, and `tell_user` to reach the user.
- Each run has its own event loop (`asyncio.run` in a worker thread): nothing async may be shared between runs (the OpenAI
  HTTP client is per model for that reason).
- Tools that fetch URLs must refuse non-public addresses (the cloud metadata service is reachable from the app).
- LangGraph's `checkpoint*` tables are not ours: Alembic ignores them (`EXTERNAL_TABLE_PREFIXES`).
- The Azure app runs with `minReplicas: 1` on purpose: the clock and dispatcher are in-process.
- The sandbox is lazy (`LazySandbox`): a waking that never runs a command or touches `/workspace` never starts it. Keep
  anything that needs the sandbox behind the backend's `execute`/upload/download, or it will wake it for nothing.
- `src/dottie_runtime/` runs inside sandboxes and is copied there as source: it must never import `dottie` (the app
  imports it, not the other way round). Anything both sides need (`DictFiles`, `ToolFilter`) lives in it.
- In `AGENT_MODE=sandbox` the sandbox gets a run token and nothing else. Do not hand it database or model credentials:
  add an `/internal` endpoint instead. `/internal` is excluded from OpenAPI (and so from the generated client).
- Routes: include the API router before `_serve_frontend`, whose catch-all would otherwise answer `/api/...`.
- Multi-user: every route that takes an id looks the thing up through `api/access.py` (`owned_dottie`, `owned_conversation`,
  `owned_schedule`) and every list filters by `user.id` (`UserDep`). A new endpoint without that is a data leak: add it to
  `tests/test_multi_user.py`. `404`, never `403`, for someone else's. With sign-in off everything belongs to the user `local`.
- `PUBLIC_URL` is the address people use (sign-in callbacks); `GATEWAY_URL` is how a sandbox reaches the callback API.
  The gateway app (`SERVE=internal`) has no sign-in middleware on purpose.
- MCP has its own gate (`McpAccess`, personal access tokens), and `/mcp` is exempt from the browser login for that reason.
- Credentials never go into a URL, a config or a log: they are secrets (`engine/secrets.py`), referenced as
  `{{secret:NAME}}` and filled in only inside the app when connecting. Log MCP servers with `mcp.describe()` (host and path),
  never the URL. The secrets API never returns a value; keep it that way, and add a test when you add an endpoint near it.
